How a pin works

The hub stores references, not files. Each listed version binds a tag to the exact commit and file contents that passed.

What the checks mean
1An author tags a release

The pack stays in the author's own GitHub repository, at a tag such as v1.0.0.

2The hub checks it

Rendering with Copier's unsafe=False, then each profile's commands: uv sync, ruff, mypy, pytest.

3The listing records the pin

Tag, 40-character commit, and a SHA-256 digest over every file's path and bytes.

4You copy one command

pytemplate-uv refuses the pack if the tag moved or any file changed, and writes nothing.

What the labels mean

Listed does not mean safe. A generated project's dependencies, build backend, and tests run code when you use them, so read a pack first.

LabelMeansDoes not mean
ListedThe pack passed the automated checks at this commitSafe, reviewed, or endorsed
ReviewedThe named maintainer reviewed this exact commitSafe or free of bugs
lifecycle passedThe commands passed with default answers, at the time of the checkOther answers or components work
licenseThe submitter's declaration, and a license file existsThe hub checked the license text
MaintainerPublished by the hub's own maintainerRanked higher: it gets no boost

How ranking works

Recommended combines three things the index can show. Nobody can pay for rank, and the maintainer's own packs get no boost.

recommended = 0.4 × trust + 0.3 × freshness + 0.3 × popularity
  trust      = 1.0 reviewed · 0.6 listed, every profile passed · 0.3 otherwise
  freshness  = 1.0 if checked in the last 30 days, falling to 0 at 365 days
  popularity = min(1, log10(1 + stars) ÷ 3)        1,000 stars = 1.0
with a search: relevance ÷ best relevance × (0.7 + 0.3 × recommended)
ties: name

Today every pack is listed, checked this week, and has no stars yet, so Recommended falls back to name order.

1. Generate a project from the bundled templates

You never install pytemplate-uv to use it: uvx pytemplate-uv@latest runs the latest release. If you prefer a pytemplate command, run uv tool install pytemplate-uv.

uvx pytemplate-uv@latest create my-tool -y
cd my-tool
uv sync
uv run pytest
uv run my_tool --help

create used the default python profile, and -y accepted the defaults instead of asking. The project comes with ruff, strict mypy, pytest, a GitHub Actions workflow, and an AGENTS.md for coding agents.

Run uvx pytemplate-uv@latest list-profiles and list-components to see what is bundled. When the bundled profiles don't fit, look on the hub.

Publish a pack

Write a template pack for the projects you start most often, keep it in your own GitHub repository, and list it with one pull request. The hub has no accounts: your repository is your profile.

1. Check that your pack can be listed

  • A contract 1 pytemplate pack at the root of a public GitHub repository, with a license file.
  • No _tasks, _migrations, _jinja_extensions, or symlinks: rendering runs with unsafe=False.
  • Lifecycle commands start with uv, for example uv sync and uv run pytest, and pass with the default answers.

2. Tag a release

git tag v1.0.0
git push origin v1.0.0

3. Add your pack to the index

In a clone of the hub:

uv run pytemplate_hub add https://github.com/<you>/<pack> --tag v1.0.0 --license MIT

4. Open the pull request

CI runs the same checks as uv run pytemplate_hub verify. When a maintainer merges it, your pack appears here with its pinned command, and a badge for your README.

Later versions

Tag again and run add with the new tag. Earlier versions stay listed until you yank one.
